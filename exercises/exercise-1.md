# Exercise 1: Persistence, SQL, ORM and migrations

Build the persistence foundation for the equipment API using SQLAlchemy, SQLite
and Alembic. Compare explicit SQL with ORM operations, and practise transactions
and schema migrations. The core implementation uses one equipment table. Slides
and lecturer narration are optional.

## Before you start

Use Python 3.11 or 3.12, a terminal and an editor. You should know Python classes,
functions, HTTP methods and basic FastAPI routes. Refresh primary keys and foreign
keys: a primary key identifies one row, while a foreign key refers to a row in
another table. A category could describe many pieces of equipment; sketch that
one-to-many relationship, but do not build a second table.

## Key ideas

**SQLAlchemy** is a Python toolkit for working with relational databases. It
provides a SQL expression system and an ORM, manages connections through an
engine, and uses Sessions to track database work and transactions. This exercise
uses SQLite as its database; SQLAlchemy is the Python layer that communicates
with it.

**ORM** means object-relational mapper. SQLAlchemy's ORM maps Python classes to
database tables and Python objects to rows. For example, an `Equipment` object
represents an equipment row; mapped attributes such as `name` correspond to
columns. You can work with those objects rather than writing every query as SQL,
while still using SQL concepts such as keys, constraints and transactions.

**Alembic** is a database schema migration tool commonly used with SQLAlchemy. A
migration records a schema change, such as creating a table or adding a column,
so the database can be upgraded to a known revision and, where supported,
downgraded. Alembic does not replace SQLAlchemy or automatically make schema
changes safe: review autogenerated migrations before applying them. In this
exercise Alembic owns schema changes; do not use `create_all()` at API startup.

## Persistence implementation — 95 minutes

### P1: Data model and first migration — 20 minutes

Interpret the model: `Equipment(id, name, category)`. Add required typed `name`
and `category` columns in `app/models.py`.

The pattern `label: Mapped[str] = mapped_column(String(30))` maps a Python string
attribute to a string column. Reuse it with the field names and lengths specified
in the TODO comments. `id` is already supplied as the primary key.

The engine manages connectivity. A `Session` tracks objects and transactions. Each
request gets a new Session from `get_session`; never make one global Session.

```bash
python -m alembic revision --autogenerate -m "create equipment"
```

Open the new Python file under `migrations/versions/`. Check that `upgrade()`
creates equipment with id, name and category, and that `downgrade()` reverses this
schema operation. Autogeneration proposes a change; you must review it.

```bash
python -m alembic upgrade head
python -m alembic current
python -m scripts.inspect_schema
```

**Checkpoint:** all three columns exist and a revision id prints. Do not add
`Base.metadata.create_all()` to application startup. Alembic owns this exercise's
schema.

### P2: SQL statements in Python — 15 minutes

Run `python -m scripts.sql_practice`. Read the supplied bound INSERT and SELECT.
`text()` represents explicit SQL. `:name` is a bound value; never join user input
into SQL with f-strings. `.mappings()` produces row mappings rather than ORM
objects.

Complete the TODOs: UPDATE the returned row by its id, check the changed value,
then DELETE that practice row. Commit after writes. Use parameter dictionaries
for every value.

**Checkpoint:** INSERT, SELECT, UPDATE and DELETE all run, and a SELECT after
deletion finds no row. Explain why `WHERE id = :id` matters.

### P3: ORM and transaction practice — 25 minutes

Run `python -m scripts.orm_practice`. `add` tracks a new object, `commit` flushes
pending SQL and commits the transaction, and `refresh` loads current column
values. `flush` alone is not a commit. The `with` block closes the Session; it
does not automatically commit uncommitted work.

Complete retrieval and update using `session.get(Equipment, item.id)` and
attribute assignment. Commit, then query again in a new Session. Leave the row in
the database. Try changing a value without committing and closing the Session:
the later Session should still see the last committed value. Explain what
rollback would discard.

Compare the two approaches on the **same** row. Parameterised SQL:

```python
row = session.execute(
    text('SELECT id, name FROM equipment WHERE id = :id'), {'id': chosen_id}
).mappings().first()
```

ORM: `item = session.get(Equipment, chosen_id)`. Explain mapping versus object. Set
`SQL_ECHO=1` in your terminal before running the ORM script to inspect generated
SQL. PowerShell: `$env:SQL_ECHO='1'`; macOS/Linux: `export SQL_ECHO=1`. Set it back
to `0` afterwards. A Session's identity map may satisfy repeated primary-key
lookups of an already-loaded object without another SELECT.

### Explicit SQL and ORM: compare

Both approaches send SQL to the same database and are managed here through a
SQLAlchemy Session. They differ in what you write and receive:

| | Explicit SQL | ORM |
|---|---|---|
| You describe | SQL statements and bound values | Operations on mapped Python objects |
| Example in this lab | `text('SELECT ... WHERE id = :id')` | `session.get(Equipment, chosen_id)` |
| You receive | Rows or mappings; choose columns and shape | Mapped objects with attributes |
| Useful when | You need direct control of a query or are learning/using SQL-specific features | You want to work with domain objects and let SQLAlchemy map rows and columns |
| Keep in mind | Bind values separately; avoid building SQL by joining user input | Understand the SQL generated and the query being made |

Neither approach removes the need to understand queries, indexes, transactions or
the schema. The ORM is not a different database and does not guarantee faster
queries. For this exercise, use the supplied explicit SQL in P2 and the ORM in P3
so you can compare their work on the same data.

**Checkpoint:** a new Session sees the saved value. SQL and ORM both execute
database operations; neither is automatically faster. Query shape, indexes and
loading matter.

### P4: Change the schema and verify — 25 minutes

Keep a record created in P3. Add `location: Mapped[str | None]` using
`mapped_column(String(60), nullable=True)` to the model.

```bash
python -m alembic revision --autogenerate -m "add optional location"
```

Review the candidate: one added nullable location column, no dropped table or
rows. Apply it with `python -m alembic upgrade head`, then run
`python -m scripts.inspect_schema` and `python -m alembic current`. Read the P3
row again: its id/name should remain and location should be `None`.

**Checkpoint:** migration file, current revision, changed schema and retained
record.

### P5: Compare and explain — 10 minutes

In three sentences explain when explicit SQL is helpful, when ORM is convenient,
and why either approach still needs transactions and migration discipline.
SQLite is embedded and stores this database in a local file. That file survives
an application restart but needs durable volume/storage in a deployed
environment. PostgreSQL runs as a server and supports network clients and
concurrent workloads. SQLite also has production uses; choose from requirements
rather than labels.

Optional configuration demonstration only:

```bash
python -m pip install -r requirements-postgres.txt
```

A PostgreSQL URL has the form
`postgresql+psycopg://USER:PASSWORD@HOST:5432/DBNAME`. Set it as
`equipment_URL` only when an actual development server and credentials exist.
`.env.example` is documentation, not an automatically loaded file. Do not put
real credentials in commits. SQLite-only `check_same_thread` settings are
conditional in `database.py`. URL changes do not migrate data or prove
portability: run migrations and integration checks against PostgreSQL
separately. No PostgreSQL server is needed for the core exercise.

## Hints and troubleshooting

| Symptom | Check and next action |
|---|---|
| Missing package | Confirm this terminal uses the repository's virtual environment |
| No such table/column | Run Alembic current and schema inspection against the same `equipment_URL` |
| Empty generated migration | Save the model file and check models are imported in `migrations/env.py` |
| Data vanishes after restart | Check commit and current working directory; relative SQLite URL uses that directory |
| `PendingRollbackError` | Roll back the failed Session before reusing it; inspect the original exception |

Hint ladder: identify the layer that owns the failure; inspect the matching TODO
and smallest failing check; then compare the earlier worked create/read pattern.
For a missed class, first complete P1–P4. Continue with Exercise 2 for CRUD, then
Exercise 3 for caching.

Stop servers with Ctrl+C. Keep your work and migration history. No cloud cleanup
is needed; ask the lecturer for help with the exact command, error and hypothesis.
